# Protocol: static versus adaptive executable checks under deployment-realistic feedback

Pre-registered on 2026-09-20 before any run, selection or endpoint read; reproduced here
verbatim apart from path names. At the time the two arms were called
`replication_v2_static` and `replication_v2_adaptive`; in this repository they are
`configs/static` and `configs/adaptive`, generated by `tools/make_configs.py`. The
`perf_v1` configs it diffs against were an earlier pair of the same arms and are not
included here.

## Question

Under deployment-realistic training feedback (out-of-fold train predictions), does
artifact-conditioned evolution of executable checks change builder behaviour or final
router performance relative to a fixed evaluation suite?

## Conditions

| | `replication_v2_static` | `replication_v2_adaptive` |
|---|---|---|
| config | `configs/replication_v2_static/task.yaml` | `configs/replication_v2_adaptive/task.yaml` |
| grader entrypoint | `RouterGrader` (fixed suite) | `AdaptiveRouterGrader` |
| identical | four `claude-opus-4-8` builders; `run.stop.max_real_attempts: 24`; seed `seed_perf_v1/` (out-of-fold `predictions_train.json`, one README paragraph saying so); task prompt block byte-identical; `train_predictions: predictions_train_oof.json` in training replays; six fixed checks; shared memory; agent prompts; `runtime_options.max_budget_usd 15`; run caps $250 / 6 h; sandbox with the private root denied; five validation slots; stopping and failure rules | same |
| only difference | — | the frozen adaptive mechanism: checkpoints at real attempts 8, 12, 16; existing proposer prompt and evidence; at most 2 checks per checkpoint, 6 per run; mechanical admission (reference passes twice, library mutant fails, a cited candidate fails); existing delivery and response instrumentation |

`diff configs/perf_v1/task.yaml configs/replication_v2_static/task.yaml` and
`diff configs/perf_v1_adaptive/task.yaml configs/replication_v2_adaptive/task.yaml`
each show two lines: the header comment and `grader.args.arm`. `diff` between the two
replication configs shows the arm label, the entrypoint, and the adaptive block. No new
roles, integrator, coaching or proposer prompt.

## Launch order

Randomized once, after the freeze commit exists and before either run:
`python -c "import hashlib,random; h=hashlib.sha256(b'<freeze-commit-sha>').hexdigest(); print(random.Random(h).choice(['static first','adaptive first']))"`.
The command, the input commit and the output are appended to this file before launch.

## Selection (the perf_v1 correction), both arms identically

Owner-side selection tooling (research materials), `--mode top5`:
1. every finalized real attempt; 2. deduplicate by solution sha256; 3. replay each
distinct candidate on the merged train trace under the run's out-of-fold predictions and
run the common fixed checks; 4. rank by out-of-fold training U; 5. the top five to
validation, SQLite-reserved; 6. select the valid candidate with maximum validation U.
Adaptive-only checks never affect eligibility or ranking; they are recorded as mechanism
outcomes (checkpoints.jsonl, deliveries.jsonl, bank versions).

## Outcomes

Primary: merged U on the fresh OOD transfer endpoint (endpoint 2: 81% MMLU-Pro, no tau2-like workload; not a reproduction of the original distribution), one read per selected router,
in the single batch of the dual-endpoint design. The original test (endpoint 1) is read in
the same batch and reported as exploratory.

Secondary: per-tenant quality, cost and lateness on both endpoints; the distribution of
out-of-fold training U over all distinct candidates per arm (not only the winner);
checks proposed / admitted / rejected with reasons; the artifact (agent, commit) that
triggered each admitted check; delivery records (feedback written) per agent; commits
after delivery that name the check's mechanism (from commit messages and diffs, by hand,
labelled as an observed sequence); whether the triggering and the terminal artifact of
each agent pass each admitted check; strategy convergence: per-agent final model-choice
rule (pred-trusting vs fitted table vs hybrid) read from the terminal solution.py.

## Claim boundary

A matched static control exists, so this experiment may support claims about adaptive
evaluation on this task. One run per arm: differences are reported with the spread of the
candidate distributions, not as significance. Fresh-family results speak to transfer to
unseen families (mostly MMLU-Pro), not to the original task.

## Failure rules

A run that stops on a cap or an infrastructure fault is reported as such and not
relaunched under this protocol without a written amendment. No endpoint result feeds back
into code, selection or rerunning.
