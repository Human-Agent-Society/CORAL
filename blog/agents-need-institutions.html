Release Notes · No. 02

Multi-agent Societies, Institutions, and Incentives

What does a society of self-improving agents need? The same things ours did: judges, city-states, archives, and privacy.

The CORAL Team July 10, 2026Accepted at COLM 2026
TL;DR

Since the launch post, CORAL was accepted to COLM 2026, placed top-3 on several kernels of NVIDIA's SOL-ExecBench — and gained the four institutions every society of agents turns out to need. Judges: rubric graders that score open-ended work no function can compute a number for. City-states: multi-island runs that keep shared knowledge from collapsing into groupthink, with migration to mix it. Archives: typed notes with provenance that turn agent memory into a knowledge graph. And privacy: OS-level sandboxing that makes secrets unreadable rather than politely off-limits.

When we introduced CORAL in March, the most striking findings weren't the benchmark numbers. They were the social behaviors: agents copying each other's breakthroughs within minutes, spontaneously authoring consensus documents, cross-referencing each other's codebases like reviewers. Give a population of autonomous agents shared memory and a scoreboard, and something that looks unmistakably like a small research community assembles itself.

Watching those communities for four months — the paper is now accepted at COLM 2026 — pushed us toward a question that sounds more like political economy than machine learning: what does a society of self-improving agents actually need? Every answer we arrived at was something human societies had already invented. Not smarter individuals — institutions: courts to render judgment where measurement fails, city-states where distinct cultures can develop, archives that make knowledge cumulative instead of anecdotal, and privacy that is enforced rather than promised. A society of agents without them hits the same walls ours would — it can only value what it can measure, it converges on monoculture, it forgets what it learned, and it keeps its secrets on the honor system.

So this release gives CORAL the same things ours got:

01 · Judges

Rubric graders for open-ended work

Societies invented courts because most disputes that matter have no formula. Every result in our launch post had a number attached — cycles, C₅, MCRMSE — which means every task we could run was one where measurement suffices. But a lot of valuable work isn't like that: a research report, a legal memorandum, a design document. If CORAL can only optimize what a Python function can score, whole domains stay outside its jurisdiction.

CORAL now incorporates an agentic judge system: the judge is itself an agent, spawned inside the grading loop, that reads the artifact and applies a rubric — returning one Score per criterion plus a weighted aggregate. You don't write grading code; the judge ships as an ordinary TaskGrader package, so you point grader.entrypoint at it and supply the rubric in grader.args. It comes in two flavors:

Fig. 1 — The judge loop: the agent produces an artifact, the judge agent applies the rubric, and each criterion returns a PASS/FAIL verdict with rationale. The aggregate is the weight-normalized pass fraction.

Option A — statutory law: you write the rubric

StrictRubricJudgeGrader applies the same criteria every eval. You write them once in task.yaml; each criterion is a binary PASS/FAIL, and the aggregate is the weight-normalized pass fraction. Deterministic, auditable, and the default choice:

task.yaml
grader:
  entrypoint: "race_japan_grader.grader:Grader"
  args:
    files: ["report.md"]          # the artifact the agent must produce
    judge_model: opus
    feedback_level: full           # full | aggregate_only | score_only
    rubrics:
      - name: "Accuracy"
        description: "Every factual claim is supported by the source material."
        weight: 2.0
      - name: "Coverage"
        description: "Addresses all required sections of the brief."
        weight: 1.0

Option B — case law: the judge develops the rubric

For genuinely open-ended tasks where you can't enumerate the criteria up front, AgentJudgeGrader generates a rubric on the first eval and evolves it as agents plateau — when everyone passes the current bar, the judge raises it, the way case law tightens with each precedent. The trade-off is a moving target: scores across evals are less directly comparable and harder to audit, so prefer the static rubric unless you truly can't pin the criteria down.

One knob deserves special mention: feedback_level. With full, agents see per-criterion verdicts and rationale — the judge's opinion becomes part of the evolutionary signal, steering the next attempt. With score_only, agents get a bare number — useful when a detailed opinion would let them overfit the judge rather than improve the work. In a system where agents optimize whatever the grader rewards, the grader is the incentive structure — so how much of the court's reasoning to publish isn't a logging option, it's incentive design, and it turns out to be one of the most interesting levers in judge-graded evolution.

When to judge, when to compute
If you can compute the number (accuracy, speedup, pass-rate), use a code grader every time — judges are slower, cost LLM calls per eval, and are noisier. Reach for a judge only when the thing you care about is quality of prose, structure, or argument. Full guide: coral.compounding-intelligence.ai/docs/guides/rubric-judge; working examples at examples/race-japan-elderly/ and examples/apex-eggshell-skull/.
02 · City-States

Islands, migration, and the value of distance

The launch post celebrated how fast knowledge diffuses between agents — a breakthrough on the leaderboard gets copied within minutes. But total connectivity is a double-edged sword, for agents as for civilizations. The same shared notes that spread a good idea also spread a mediocre one: once the population converges on a single approach, nobody is left exploring the alternatives. Distinct intellectual traditions need distance to develop — which is why evolutionary computation rediscovered geography under the name of the island model.

CORAL now supports it natively. One line splits a run into isolated islands:

shell
coral start -c task.yaml agents.count=4 islands.count=2
# or in task.yaml:  preset: multi-island

Agents on the same island share everything — attempts, notes, skills, heartbeat state. Agents on different islands receive separate shared-state views through their normal workspace and CLI interfaces, so each island can develop its own culture of approaches. Islands are named after legendary isles (atlantis, avalon, lemuria, ...), and an agent's id carries its birthplace as readable provenance — poseidon-from-avalon stays poseidon-from-avalon even after emigrating. Inside a worktree, every CLI command (coral status, coral log, coral notes) automatically scopes to the agent's current island.

Fig. 2 — Two islands, each with its own shared knowledge layer. Every migration.every finalized real evaluations, CORAL runs a migration cycle that may relocate eligible agents; a migrant's worktree and eval history travel with it, its notes stay behind, and it announces itself with an arrival note under notes/migrations/.

Migration

Isolation without mixing just gives you N smaller runs — what made the city-states fertile was the travelers between them. Migration is enabled by default whenever islands.count > 1: every migration.every finalized real evaluations, CORAL runs a cycle that ranks agents by their best score over a recent window and may relocate up to max_per_cycle eligible agents to another island (weighted toward the weakest eligible destination by default), without worsening roster balance. A 100-real-evaluation remigration cooldown prevents the same high-scoring agent from immediately bouncing between islands. The migrant's worktree, branch, and eval history travel with it — but its notes stay on the source island. Ideas travel in the migrant's head, not as a bulk export of the old island's library.

Does it help—and does it scale?

We ran a small validation on Kernel Builder, a real coding task in which agents optimize a GPU kernel under a shared 16-evaluation budget. Four OpenCode agents running mafia/glm-5.2 used one of four topologies: global (one shared knowledge pool), partition (two isolated islands), multi-island (two islands with selective migration), or independent (four one-agent islands). Each topology has only three operational repetitions, so the results are descriptive rather than a powered causal test.

TopologyFinal gain, mean [95% interval]Best-so-far AUCn
Global41.1 [0.0, 68.3]16.53
Partition31.4 [12.9, 63.7]9.03
Multi-island49.7 [13.2, 68.0]17.43
Independent31.6 [0.3, 81.7]6.83

Multi-island has the strongest mean: +8.6 percentage points over global, +18.4 over partition, and +18.1 over independent search. But the intervals are wide, and final solution diversity is lower than global's. We read this as evidence that distance plus selective exchange can help allocate a small, failure-prone search budget—not as proof that migration is generally better.

The central scaling question is still open
Every condition above uses exactly four agents. It tests topology at one population size; it does not test whether multi-island helps multi-agent systems scale as more agents join. The important experiment is an agent-count × topology sweep on real tasks: compare global and multi-island runs as the population grows, under both a fixed total budget and a fixed per-agent budget, and measure performance alongside sample efficiency, wall-clock time, and cost. Until that curve is measured, we make no claim that city-states improve multi-agent scaling.
A synthetic failure mode
We also tested hidden NK landscapes and a larger scripted black-box sweep. These are deliberately artificial controls: agents manipulate bit strings, see scalar scores, and do none of the semantic collaboration that makes a real coding task social. Migration did not consistently help; on the smooth control it was worse than faster global sharing, and an apparent advantage in part of the harder sweep did not remain stable in fresh confirmation. The useful lesson is a boundary condition, not a benchmark claim: islands can waste coordination budget or slow the spread of a good approach when the task does not benefit from separate intellectual lineages. The synthetic result points to that potential failure mode, but it does not estimate how city-states perform on real agent work. Data and analysis remain available in the original run-level table and scripted sweep.

That design choice took us a few iterations to get right, and it raises the question the next institution answers: if knowledge belongs to the island rather than the agent, what exactly is a unit of knowledge?

03 · Archives

Notes with provenance

Societies became cumulative when they started writing things down — and became scientific when records gained provenance: who claims this, based on what evidence, superseding which earlier belief. In the launch post's experiments, notes were free-form markdown, and agents did remarkable things with them, from consensus documents to cross-agent comparative analysis. But free text drifts as runs grow: experiments get repeated because nobody marked the dead end, conclusions float loose from the attempts that produced them, and a note that refutes an earlier idea sits next to it in the directory with equal apparent authority. An archive where every document has equal standing is a pile, not an archive.

Notes now carry an optional structured-trace schema in their frontmatter. A note is no longer just prose — it's a typed claim with provenance:

markdown — note frontmatter
---
creator: captain-nemo
type: experiment        # experiment | hypothesis | dead_end | open_question | synthesis
claim: "matmul inner-loop tiling at tile=32 improves score"
based_on: a3f9c2        # the attempt this builds on
evidence:
  attempt: 7b1e4d       # the graded artifact behind the claim
confidence: medium      # low | medium | high
status: confirmed       # confirmed | refuted | untested
supersedes: [research/old-idea.md]
---

Fig. 3 — The archive as a graph. Typed frontmatter links (supersedes, refutes) and ordinary body links become edges; the dashboard's Knowledge tab renders it live, with nodes sized by confidence and colored by claim status.

Three things fall out of this:

  • Claims have provenance. based_on and evidence.attempt tie every claim to the graded commits behind it — a conclusion is one hop from the experiment that produced it.
  • Knowledge has standing. A dead_end with status: refuted reads very differently from a hypothesis with status: untested — and agents (and heartbeat prompts) can treat them differently, instead of granting every old note equal authority.
  • The archive has structure. Typed links plus ordinary markdown/wiki links in the body become edges of a graph, so a run's intellectual history — including which lines of inquiry died — is visible at a glance.

Everything is backward compatible: a plain free-text note still works, and because body links also count as edges, the graph populates even on old runs. A new bundled create-notes skill teaches agents the schema with four note variants and a self-audit checklist, so structured notes are what agents write by default rather than something you have to prompt for.

04 · Privacy

Sandboxing, enforced

Societies need privacy as much as they need openness: exams only work if the answer key is sealed, and no one joins a society that can rifle through their belongings. Both concerns are literal in CORAL. Hidden task data and the grader venv live in .coral/private/ — an agent that can read the answer key isn't evolving, it's cheating — and the agents run on your machine, next to ~/.ssh and every other run's data. Until now, both were protected by policy, not architecture: runtime permission settings plus instructions in CORAL.md. Privacy-by-request is fine for well-behaved runtimes; it is not a security boundary, and every new runtime we added (Codex, Cursor, Kiro, OpenCode) meant another permission dialect to keep honest.

Now the boundary is structural. agents.sandbox wraps every agent subprocess in an OS-level sandbox — Anthropic's sandbox-runtime (srt: Seatbelt on macOS, bubblewrap on Linux) — uniformly across all runtimes.

Fig. 4 — The sandbox boundary. Reads inside the agent's slice of the run succeed; reads of .coral/private/, host secrets, and other runs are blocked by the OS — Seatbelt on macOS, bubblewrap on Linux — identically for every runtime.

  • Reads are allow-listed: the agent's own worktree (and same-island siblings'), the run repo, shared .coral/ state minus private/, the surfaced grader source, and toolchain dotdirs.
  • Writes are allow-listed to the agent's worktree, the run's non-private .coral/ state, repository metadata needed for commits, toolchain dotdirs, and /tmp.
  • Network comes in two modes: open (full access, mediated by an allow-all proxy the manager runs in-process) or allowlist (traffic restricted to allowed_domains).
shell
npm install -g @anthropic-ai/sandbox-runtime   # once (Linux also: bubblewrap, socat, ripgrep)
coral start -c task.yaml agents.sandbox.enabled=true
# or in task.yaml:  preset: sandbox

A detail we're fond of: the per-agent sandbox policy lives under .coral/private/sandbox/ — the manager reads it host-side before the sandbox exists, and the sandbox then denies the agent access to the very file that defines its own boundaries. What should be open stays open — agents can read the grader's source to understand exactly how they're judged — and what must be private stays private, without depending on anyone's good manners.

The provider is pluggable: agents.sandbox.provider takes the built-in srt or any module.path:ClassName implementing the SandboxProvider protocol — the hook for hosted backends like e2b or Modal. (For container-based isolation, run.session=docker now also runs agents as an unprivileged OS user; the two mechanisms solve the same problem and are mutually exclusive.)

And the institutions compose. In a multi-island sandboxed run, the sandbox's worktree allow-list follows island membership — so when migration moves an agent, the manager resyncs the sandbox boundaries of live bystanders on the affected islands (sessions are interrupted and resumed; no work is lost). Judged by courts, organized into city-states, recorded in archives, with privacy the OS enforces: each institution stands alone, but they were designed to govern together.

05 · Public Works

The operator's workbench

Every society also needs its unglamorous infrastructure — roads, plumbing, permits — and so does every framework. Alongside the four institutions, a steady stream of changes improved what it's like to operate a run: configuring tasks, wiring up runtimes, and steering long experiments.

Authoring & setup:

  • Packaged graders, everywhere. Every grader is now a proper package resolved from grader.entrypoint inside an isolated venv (the legacy eval/grader.py auto-discovery is gone — a breaking change). Hidden data is declared in grader.private; everything else in the grader package is deliberately surfaced read-only to agents, so they can study exactly how they're scored without being able to touch it.
  • task.yaml presets. A top-level preset: pulls in a built-in or local base config (multi-island, sandbox, docker-opencode, ...) with task keys always winning — common topologies become one line.
  • User-level agent bindings. coral setup scans your PATH for installed runtimes and saves named bindings (claude-opus, codex-mini, ...) to ~/.config/coral/agents.yaml; task configs reference them with agents.binding, and coral agents doctor live-checks each one with a hello ping.
  • A multi-harness plugin. The plugin/ directory drives CORAL from inside Claude Code or Codex — skills for quickstart, task authoring, and run babysitting, installable from the repo as a marketplace.

Run operations:

  • Experiment DAG view + attempt export. The dashboard renders the full attempt lineage as a DAG, and coral export <hash> -b <branch> turns any attempt into a normal git branch for downstream use.
  • Steer on resume. Queue instructions for a stopped run from the dashboard; coral resume drains them into the agents — including --from <hash> to fork an agent from any past attempt.
  • Auto-stop limits. run.stop.max_real_attempts=30 ends a run after N finalized attempts — budget control for unattended runs.
06 · Getting Started

Try it — the institutions compose

Everything above is on main. The institutions compose, so a judged, partitioned, privacy-enforced run is a one-liner away:

shell
git clone https://github.com/Human-Agent-Society/CORAL && cd CORAL && uv sync
coral setup                        # detect installed runtimes, save bindings
coral start -c examples/circle_packing/task.yaml \
    agents.count=4 islands.count=2 agents.sandbox.enabled=true

Guides for each institution: rubric judges, multi-island runs, and the documentation site for the rest. To port your own benchmark, coral init my-task scaffolds the task package and coral validate my-task dry-runs your grader before you spend a single agent-hour.

The launch post closed by asking what organizational principles for machine intelligence might look like. Four months in, our working answer is the one this post opened with: the same things ours needed — judges, city-states, archives, and privacy. How a society of agents is judged, partitioned, recorded, and bounded matters as much as how capable its members are. And the list of institutions agent societies don't have yet is long: peer review, reputation, markets, elections — the incentive structures human societies took centuries to invent. Some of those are less absurd than they sound, and the whole system is open — come build them with us.
